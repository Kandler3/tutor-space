# Подготовка к защите ЕК1

[Паспорт](../PROJECT.md) · [SR](requirements.md) · [T](threat-model.md) · [D](design-decisions.md) · [вклад](../CONTRIBUTIONS.md)

ЕК1 проверяет концепцию безопасности и запускаемую основу. Очный слот — около шести минут на команду; презентация не требуется. [Регламент курса](https://github.com/hse-rbpo-bachelor-2026/course/blob/e7ec47288ca9f7bc59dab3f4f8d52a1bef7d67b1/assessment/EK1.md).

## Личная проверка перед записью вклада

Это инструкция для предстоящей работы участников. Выполнение помощником этих команд не подтверждает личную проверку M1/M2.

### M1 — бэкенд: аутентификация, сессии и данные

1. Прочитать [запуск](../README.md#локальный-запуск), обработчики [API](../internal/api/server.go), [пароли](../internal/auth/password.go), [сессии](../internal/auth/session.go) и [SQL](../internal/store/store.go). Найти, где субъект берётся из сессии, где проверяется срок и что меняет logout.
2. При запущенном Docker выполнить в первом терминале:

   ```sh
   ./scripts/run-local.sh
   ```

   Во втором терминале:

   ```sh
   python3 scripts/smoke.py
   go test ./...
   go vet ./...
   ```

   Smoke должен подтвердить регистрацию, вход, свой профиль, отказ без сессии/при неверном пароле и отзыв токена. Если проверка не прошла, сначала записать и устранить причину. Тест с настоящей отдельной БД запускается по команде из README; без `TEST_DATABASE_URL` он пропускается.
3. Прочитать [D-01](design-decisions.md#d-01). Объяснить, как оба варианта обеспечивают немедленный отзыв, зачем JWT-варианту состояние `sid`, почему подпись не заменяет отзыв и какой ценой выбранный серверный токен зависит от БД. Сверить это с тестом двух независимых экземпляров обработчика в `TestIntegrationAuthenticationLifecycle`.
4. Прочитать [контрпример D-03](design-decisions.md#контрпример-оценка-относится-к-другому-тексту). Проверить, что блокировка строки и проверка `expected_revision` решают разные задачи. Предложить уточнение или записать собственное обоснование сохранённого решения и его будущей проверки.
5. В своём разделе CONTRIBUTIONS записать команды, наблюдаемые результаты и конкретные выводы по D-01/D-03. «Всё проверил» без результата не показывает содержательную проверку.

### M2 — бэкенд: валидация, доступ и целостность операций

1. Прочитать [серверный разбор входных данных](../internal/api/input.go), два сценария [паспорта](../PROJECT.md), SR-03/SR-04/SR-06/SR-07 и [D-02](design-decisions.md#d-02). Найти, где сервер отклоняет неизвестные поля и ограничивает размер запроса. На уровне проектных правил пройти сценарий двух пар: кто может создать новый объект, кто может принять приглашение, кому остаются старые задания после прекращения связи и почему новый репетитор не получает историю.
2. На работающем локальном сервере выполнить две отрицательные проверки:

   ```sh
   curl -i 'http://127.0.0.1:8080/api/me?user_id=another_user'
   curl -i http://127.0.0.1:8080/api/register \
     -H 'Content-Type: application/json' \
     -d '{"login":"ek1_m2_check","password":"LocalDemoPassword123!","name":"Учебная проверка","role":"student","student_id":"another_user"}'
   ```

   Ожидаются `401` без профиля и `400 invalid_json`. Это подтверждает обязательность сессии и отказ неизвестному входному полю. Эти два запроса не доказывают объектную авторизацию будущих домашних заданий: соответствующие критерии пока являются планом.
3. Разобрать [T-05](threat-model.md#t-05) → [SR-06](requirements.md#sr-06) → [контрпример D-03](design-decisions.md#контрпример-оценка-относится-к-другому-тексту): репетитор прочитал v1; ученик законно отправил v2; затем пришла оценка v1. Объяснить, почему все проверки роли/владения и короткая транзакция могут пройти, а результат всё равно будет неверным.
4. Содержательно сверить план будущего теста: `expected_revision=1` при текущей ревизии 2 должен получить `409`; текст, ревизия, статус и отсутствие оценки должны сохраниться. Отдельно объяснить оба порядка конкурирующих записей. Предложить конкретное уточнение либо записать, почему критерий SR-06 и план теста D-03 покрывают эти случаи. Это проверка проекта механизма; API домашних заданий пока не реализован.
5. Прочитать сравнение [D-01](design-decisions.md#d-01): назвать цену немедленного logout и условие перехода к автономной проверке JWT. Записать собственные выводы, выполненные команды и исправления в CONTRIBUTIONS, затем обновить свою фактическую проверку в AI_USAGE.

Для личных 10 нужны вся база и наблюдаемый вклад в оба повышенных уровня; для 9 — вся база и хотя бы один. Один участник может представлять контрпример, другой — сравнение, но для 10 каждый должен понимать и лично подтвердить оба уровня. Адресный вопрос может получить любой участник; отдельный контрпример для каждого не требуется.

## Вопросы для самопроверки

| Вопрос | Содержание ответа |
| --- | --- |
| Почему строковая блокировка не закрывает T-05? | Она упорядочивает нынешнюю запись, но не знает, какую ревизию репетитор прочитал в уже завершённом GET |
| Почему `expected_revision` из клиента допустима? | Это сравниваемое условие команды; сервер сам хранит и увеличивает ревизию. Клиент не задаёт новое значение ревизии |
| Что проверяет тест с барьерами? | Фиксирует нужный порядок чтения/отправки/проверки и оба порядка конкурирующих записей; проверяет строки БД после отказа, а не только HTTP-код |
| Зачем JWT-варианту запись `sid`? | Подпись и `exp` не сообщают о logout. При немедленном отзыве каждый новый запрос сверяет действительность сессии с общим состоянием |
| Почему выбрана непрозрачная сессия? | При уже необходимой PostgreSQL она выполняет ту же гарантию с меньшим протоколом. Цена — зависимость защищённых запросов от БД |
| Как пересмотреть выбор? | Согласовать допустимое окно отзыва и права при автономных сервисах; автономность нельзя обещать вместе с прежним мгновенным отзывом без механизма распространения состояния |
| Почему новый репетитор не получает старые задания? | Согласие на новую связь даёт новые действия, а старый объект хранит неизменяемую исходную пару участников |
| Что не подтверждено запуском? | Предметные проверки расписания/заданий, TLS и защита сетевого развёртывания; будущие проверки остаются планами |
| Что защищает Argon2id? | Замедляет офлайн-перебор хеша. Два слота ограничивают память, но не число попыток входа; это не полноценная защита от онлайн-перебора |
| Что лично сделал участник? | Материал, конкретное действие, собственный вывод или исправление и ссылка; только фактически выполненные результаты |

## Перед предварительной сдачей

- Уточнить объявление S05: срок, канал, закрытую регистрацию, согласование двух участников и результат калибровки. Статус паспорта обновляется по фактическому согласованию.
- После личной проверки заполнить CONTRIBUTIONS и AI_USAGE; пройти все приоритетные цепочки по ссылкам.
- Зафиксировать существующий commit оцениваемой версии и передать URL репозитория + полный hash через объявленный канал. PR сам по себе не является сдачей.
- Если выбран tag `ek1`, создать его на согласованной версии и не перемещать после сдачи без согласования преподавателя.
- Прийти на очную защиту и отвечать самостоятельно без ИИ. Наличие сильных материалов само по себе не гарантирует оценку 10.
