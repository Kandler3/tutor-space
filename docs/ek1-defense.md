# Подготовка к защите ЕК1

ЕК1 — концепция безопасности и подтверждение запуска основы. Ориентир очного слота — около шести минут на команду. Отдельная презентация не нужна: показывайте материалы в репозитории. [Регламент курса](https://github.com/hse-rbpo-bachelor-2026/course/blob/a25f23a49dcbf51bc7004dda75c735f5208422be/assessment/EK1.md).

## Перед предварительной сдачей

- Уточните у семинариста срок, канал сдачи, согласование двух участников и результат ранней калибровки. В паспорте по-прежнему честно указан статус «черновик».
- Каждый прочитайте документы и самостоятельно запустите основу по [README](../README.md#локальный-запуск).
- Уточните личные результаты в [CONTRIBUTIONS.md](../CONTRIBUTIONS.md) и фактическую человеческую проверку в [AI_USAGE.md](../AI_USAGE.md). Не приписывайте себе действия помощника или другого участника.
- Пройдите по ссылкам для всех приоритетных угроз; понимайте, какие механизмы уже реализованы, а какие только спроектированы.
- После проверки зафиксируйте оцениваемую версию. Передайте URL + полный commit hash через объявленный канал до его срока. Если сдаёте tag `ek1`, он должен указывать на существующий доступный commit и не перемещаться после сдачи без согласования.

## Порядок рассказа

**Первые 30–40 секунд:** TutorSpace связывает репетитора и ученика для занятий и домашних заданий. В целевом продукте два сценария: бронирование занятия и выполнение задания с результатом проверки. На ЕК1 уже запускаются пользователи и сессии; предметные модули пока планируются.

**До двух минут на центральную цепочку:** выберите угрозу доступа к чужому решению или занятиям через подменённый ID. Покажите соответствующий T, критерий SR и D о серверной проверке роли, владельца и подтверждённой связи. Объясните, почему одинаковая роль не даёт доступа к чужому объекту и почему автоматическое создание связи по двум клиентским ID опасно. Завершите конкретным будущим отрицательным тестом и ожидаемым неизменным состоянием. Точные ID возьмите из [модели](threat-model.md) и [решений](design-decisions.md), а не придумывайте на защите.

**Подтверждение основы:** покажите команду запуска, `GET /readyz` и регистрацию → вход → `/api/me`. Объясните, что профиль сохраняется в PostgreSQL, а `/api/me` определяет человека по сессии. По запросу покажите отказ без токена или после выхода. Эти проверки не подтверждают пока не реализованный доступ к домашним заданиям.

**Оставшееся время:** каждый самостоятельно отвечает на адресный вопрос о своём проверенном результате. Не пересказывайте весь паспорт. Во время ответов ИИ не используется.

## Вопросы для самопроверки

| Вопрос | Что важно уметь объяснить |
| --- | --- |
| Чем SR отличается от бизнес-правила? | Какое нарушение безопасности предотвращается и какой наблюдаемый результат его проверяет. Не любое условие продукта автоматически SR. |
| Где граница доверия? | Запросы клиента не считаются достоверными: токен, роль, ID объектов, текст и размеры проверяет сервер. Сервер обращается к БД со своей технической учётной записью. |
| Почему проверки роли мало? | Два ученика имеют одну роль, но разные задания. Нужно проверить отношение конкретного пользователя к конкретному объекту. |
| Почему связь должна подтверждаться? | Иначе один пользователь создаст отношение с чужим ID и получит привилегии. Для новых действий связь должна быть принятой и активной. |
| Почему непрозрачная сессия? | Сервер может проверить срок и отозвать сессию при выходе; цена — запрос к БД на каждом аутентифицированном запросе. Токен клиента случаен; в БД только его хеш. |
| Что даёт Argon2id? | Вместо открытого пароля хранится результат медленного хеширования с отдельной случайной солью. Это затрудняет перебор при утечке БД, но не защищает украденный действующий токен. |
| Как предотвратить двойное бронирование? | Будущее решение должно объединить проверку и изменение в транзакции с блокировкой общего интервала. Отдельная предварительная проверка на клиенте недостаточна. |
| Почему нет готовых тестов всех D? | ЕК1 оценивает концепцию и будущие проверки; полная реализация сценариев к этой точке не требуется. Запускаемая основа уже требуется. |
| В чём ограничения текущей версии? | Локальный HTTP, отсутствие предметных обработчиков и защиты сетевого развёртывания; факт запуска не доказывает все SR. |
| Что лично сделал участник? | Конкретный результат, собственная проверка/уточнение и прямая ссылка; только то, что фактически выполнено. |

Этот файл помогает подготовиться и не заменяет личное понимание, предварительную сдачу или очную защиту.
