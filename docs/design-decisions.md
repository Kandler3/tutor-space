# Проектные решения безопасности TutorSpace

[Паспорт](../PROJECT.md) · [Требования](requirements.md) · [Угрозы](threat-model.md)

D-01 и ввод/SQL в D-03 относятся к работающей основе. D-02, расписание и задания в D-03 — планы. Ниже описаны причины выбора и будущие проверки; результаты запуска приведены в [README](../README.md).

## D-01

**Выбор: случайный токен и серверная сессия.** Одному Go API уже нужна PostgreSQL. Требуется немедленный отзыв после logout и хранение секретов в виде хешей.

**Механизм:** пароль — Argon2id (19 MiB, 2 прохода, параллелизм 1, случайная соль 16 байт). Токен — 32 случайных байта, RawURL base64; в БД — SHA-256, пользователь и срок выдачи + 24 часа. Каждый защищённый запрос проверяет запись и срок, logout удаляет запись. Субъект берётся из сессии; при ошибке БД профиль не выдаётся. Хеши/DSN не попадают в ответы и логи.

В каждом экземпляре API одновременно выполняются максимум два вычисления пароля; при двух занятых слотах следующий запрос регистрации/входа получает `503 authentication_busy` и `Retry-After: 1`. Это ограничение экземпляра API, а не общий лимит для нескольких процессов. Из БД принимается только поддерживаемый профиль Argon2, без произвольных затрат из повреждённого хеша.

**Связи:** [T-01](threat-model.md#t-01), [T-07](threat-model.md#t-07) → [SR-01](requirements.md#sr-01), [SR-02](requirements.md#sr-02), [SR-08](requirements.md#sr-08).

**Альтернативы при одинаковом требовании немедленного отзыва:**

| Вариант | Как работает отзыв | Цена и условия |
| --- | --- | --- |
| Случайный токен + PostgreSQL — выбран | Каждый запрос ищет сессию по хешу; после удаления все процессы с общей БД отклоняют токен | Обращение к БД на каждый защищённый запрос; без БД нет доступа. Для одного API не нужны подпись и ключи |
| JWT с `sub`, `sid`, `exp` + общее состояние сессии | Каждый запрос проверяет подпись, срок и действительность `sid`; logout отзывает `sid` | Та же зависимость от БД для немедленного отзыва, плюс ключи, ротация, алгоритм, `iss`/`aud`. Полезнее нескольким сервисам для проверки происхождения токена |

**Почему первый:** при одной PostgreSQL он обеспечивает ту же гарантию проще. В обоих вариантах актуальные предметные права проверяются по серверным данным. JWT не обязан содержать роль; если права в claims используются без сверки, отдельно возникает их устаревание.

**Когда пересмотреть:** автономным сервисам может понадобиться работа без хранилища сессий. JWT только с подписью и сроком допускает её, но копия токена действует до истечения: удаление у клиента не выполняет нынешний SR-01. Потребуется согласовать окно отзыва/изменения прав либо механизм распространения отзыва.

**Будущие проверки:**

1. По SR-02 сверить разные соли одинаковых паролей, отсутствие исходных секретов и отказ при предъявлении `token_hash`.
2. По SR-01 проверить профиль и неверные/истёкшие токены. На двух процессах API: токен принят обоими → logout первого возвращает `204` → второй получает `401` по сохранённой копии до истечения 24 часов.
3. При остановленной БД действующий токен не даёт профиль (5xx); logout не сообщает успешный отзыв. После восстановления неотозванный действующий токен работает; успешный logout затем даёт `401`.
4. По SR-08 проверить ответы и логи с тестовыми маркерными секретами. Занять два слота хеширования: третий запрос — `503` без записи, после освобождения обработка возобновляется. Неподдерживаемый хеш отклоняется без затрат по его параметрам.

**Ограничения:** копия bearer даёт доступ до отзыва/срока; уже аутентифицированный параллельно с logout запрос может завершиться. Срок абсолютный, без refresh. Argon2 замедляет офлайн-перебор, два слота ограничивают память; это не ограничение числа попыток входа. Внешняя сеть требует TLS и защиты от перебора; злонамеренный администратор вне модели.

**Что испытано:** [интеграционный тест](../internal/api/integration_test.go) проверяет общий отзыв между двумя обработчиками с отдельными пулами и ошибку без профиля при закрытом пуле. Это один OS-процесс, а не два процесса или остановка всей БД. [Результаты запуска](../README.md).

## D-02

**План: роль, согласие и участники объекта.** Роль разрешает вид действия; активная связь — создание новых совместных объектов; исходные участники — доступ к конкретной истории.

**Правила:**

- Субъект берётся из сессии. Автор нового задания/интервала назначается сервером; ученик проверяется по активной связи. Задания и занятия сохраняют исходных участников. Списки и отдельные объекты фильтруются на сервере.
- Для пары одна запись связи: `pending → active`, затем прекращение. Принять может только приглашённый ученик; прекратить — любая сторона. Повторное приглашение прекращённой связи возвращает `pending` и требует нового принятия; клиент не меняет участников.
- Создание объекта и проверка `active` выполняются в одной транзакции с блокировкой строки связи. Прекращение использует ту же блокировку: если оно закоммичено первым, создание отклоняется; созданный раньше объект остаётся историей.
- Старые работы доступны только исходной паре, с отправкой/проверкой до окончательного результата. Старое занятие видят и отменяют его участники независимо от текущей связи. Новый репетитор не получает историю.
- Чужой/несуществующий объект — одинаковый `404` без данных и изменений; недоступный роли вид действия — `403`.

**Почему:** роль, согласие и владение имеют разные смыслы и сроки действия. UUID затрудняет угадывание, но не защищает известный ID; ограничения клиентского интерфейса обходятся обычным HTTP-запросом.

**Связи:** [T-02](threat-model.md#t-02), [T-03](threat-model.md#t-03), [T-04](threat-model.md#t-04), [T-05](threat-model.md#t-05) → [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04), [SR-06](requirements.md#sr-06).

### Контрпример к правдоподобной цепочке

**Исходное предположение:** достаточно роли репетитора и связи с учеником (T-02 → SR-03 → D-02).

**Сценарий:** посторонний C регистрируется репетитором и сам создаёт активную связь с A. Если список использует только текущую связь, C получает старые работы A от B. Тест двух несвязанных пар это не обнаруживает.

**Уточнение:** [T-03](threat-model.md#t-03) → [SR-04](requirements.md#sr-04) требует принятия приглашения; [SR-03](requirements.md#sr-03) закрепляет историю за исходной парой даже после добровольного принятия нового репетитора.

**Будущие проверки:** две пары — чужие GET/списки/изменения дают отказ без изменения БД. До принятия C → A создание заданий и бронирований запрещено; посторонний не принимает приглашение. После принятия создание разрешено, старые B/A недоступны C. После прекращения создание новых заданий и бронирований B/A запрещено; история, отправка и проверка решения старого задания до окончательного результата и отмена старого занятия доступны исходной паре. Конкурентные прекращение/создание проверяются в обоих порядках commit.

**Ограничения:** согласие не подтверждает квалификацию. Передача истории, администратор и модерация не предусмотрены. Принятая политика сохраняет доступ исходных участников к старым объектам; её изменение требует обновить паспорт, SR и планы тестов.

## D-03

**Выбор: проверенный ввод и атомарные изменения в PostgreSQL.** Ввод/SQL уже реализованы; предметные транзакции ниже планируются.

| Область | Механизм |
| --- | --- |
| Ввод | Только разрешённые поля и типы, один JSON, максимум 4096 байт; отклонять повторные/неверно регистрированные ключи и некорректный UTF-8. Пределы полей — [SR-07](requirements.md#sr-07) |
| SQL и ошибки | Значения через параметры `pgx`; динамические части только из серверного списка. Ответы/логи без сырого SQL, DSN и секретов |
| Бронирование | Транзакция: блокировать связь, проверить `active`, блокировать интервал, создать занятие. Частичный уникальный индекс допускает одно активное занятие; доступность выводится из него, без отдельного флага |
| Отмена | Блокировать тот же интервал, перечитать занятие и проверить участников. Менять только X: `active → cancelled`; повтор X не меняет Y. Активная связь для отмены старого занятия не нужна |
| Интервалы | Создание блокирует строку репетитора и проверяет `start < end` и отсутствие пересечения `[start, end)`. Соседние интервалы разрешены |
| Решение и оценка | Статусы: `issued → submitted → reviewed`; до проверки текст заменяем. Отправка/проверка блокируют одну строку и проверяют участников. Отправка увеличивает серверную ревизию. Оценка требует совпадения `expected_revision`; результат и переход в `reviewed` атомарны, после него замена запрещена |

**Почему:** параметры отделяют данные от SQL, валидация ограничивает команду, транзакции связывают проверку с записью, ограничения БД сохраняют инварианты между процессами. Проверка «свободен» только в Go имеет окно гонки; один уникальный индекс не определяет правильную отмену. Mutex одного процесса недостаточен для нескольких API.

**Связи:** [T-04](threat-model.md#t-04), [T-05](threat-model.md#t-05), [T-06](threat-model.md#t-06), [T-07](threat-model.md#t-07), [T-08](threat-model.md#t-08) → [SR-05](requirements.md#sr-05), [SR-06](requirements.md#sr-06), [SR-07](requirements.md#sr-07), [SR-08](requirements.md#sr-08). Субъект — [D-01](#d-01), участники — [D-02](#d-02).

### Контрпример: оценка относится к другому тексту

**Исходное предположение:** роль, владелец, `submitted` и блокировка строки достаточны; проверка «после `reviewed` отправка запрещена» подтверждает T-05 → SR-06 → D-03.

**Сценарий:** ученик отправляет v1 → репетитор читает v1, GET заканчивается → ученик сохраняет v2 → репетитор оценивает прочитанную v1. Роль, владелец и статус верны; блокировка при последней записи не знает о прежнем чтении. Оценка ошибочно прикрепляется к v2 даже без одновременных SQL-запросов. Старый тест этого не обнаруживает.

**Уточнение цепочки:** [T-05](threat-model.md#t-05) учитывает устаревшее чтение, [SR-06](requirements.md#sr-06) требует оценивать просмотренную ревизию. Команда передаёт `expected_revision`: под блокировкой сервер сравнивает её с текущей. Несовпадение — `409` без изменения текста, ревизии, статуса, оценки и комментария. Совпадение — атомарная запись результата, проверенной ревизии и `reviewed`. Клиент передаёт условие сравнения, а не назначает серверную ревизию. D-02 остаётся необходимым для прав.

Это проектный разбор будущего модуля, а не заявление о найденной или испытанной ошибке.

**Будущие проверки D-03:**

1. По SR-07/SR-08 проверить границы ввода, SQL-фрагменты и ошибки: отказ не создаёт запись и не раскрывает секреты. Каждый новый SQL-запрос отдельно проверить на параметризацию.
2. По SR-05 на двух процессах с общей БД: конкурентное бронирование — один успех, один `409`, одна активная запись; повтор отмены X не меняет Y. Конкурентные пересекающиеся интервалы — один успех; соседние допустимы. Ошибка внутри транзакции не оставляет частичных изменений.
3. Для v1/v2 использовать барьеры, без случайной гонки или `sleep`: прочитать v1/ревизию 1 → дождаться commit v2/ревизии 2 → оценить с `expected_revision=1`. Ожидается `409`; снимок БД прежний: v2, ревизия 2, `submitted`, оценки/комментария/проверенной ревизии нет. Чтение и оценка ревизии 2 успешны; отправка v3 после проверки — `409` без изменений.
4. На двух соединениях барьерами проверить оба порядка: оценка v2 первой закоммичена — отправка v3 отклоняется; v3 первой закоммичена — оценка ревизии 2 отклоняется, v3 остаётся без оценки. Проверять строки БД, не только HTTP-коды.
5. Прекращение связи и создание — по плану D-02. Чужие ID не меняют строки.

**Ограничения:** транзакции короткие, с context/timeout и одинаковым порядком блокировок (связь перед интервалом/заданием, если нужна). Схему и таймауты подтвердить при реализации; удаление/перенос интервалов потребуют согласованного правила. Предел тела не ограничивает частоту запросов, параметризация не заменяет права, доверенный оператор может обойти прикладные правила напрямую.
