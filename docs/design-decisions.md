# Проектные решения безопасности TutorSpace

[Паспорт](../PROJECT.md) · [Требования](requirements.md) · [Модель угроз](threat-model.md)

Статус: черновик EK1 с использованием ИИ, требующий проверки участниками. В D-01 и части D-03 выбран механизм минимальной основы; D-02 и предметные транзакции D-03 — проект будущих модулей. Описанные проверки являются планами и не доказывают, что механизм реализован или проверен. Для EK1 достаточно подтвердить запускаемую основу и объяснить эту концепцию; полный продукт здесь не заявлен.

## D-01

**Серверные сессии и раздельное хранение секретов.**

**Контекст:** пароль подтверждает аккаунт при входе, а дальнейшие запросы выполняются с bearer-токеном. Для одного Go API уже требуется PostgreSQL; внешнего провайдера идентичности и нескольких автономных сервисов нет. Выход должен прекращать конкретную сессию немедленно, а случайная копия БД не должна выдавать готовые для предъявления токены.

**Решение:**

- При регистрации сохранять Argon2id-хеш пароля: случайная соль 16 байт, память 19 MiB, 2 прохода, параллелизм 1. Сохранять параметры вместе с хешем; исходный пароль не сохранять. Вход сверяет пароль с хешем.
- При каждом успешном входе создавать новый токен из 32 байт `crypto/rand`, передавать его клиенту как RawURL base64. В `sessions` хранить SHA-256 токена, `user_id` и абсолютный `expires_at`, вычисляемый сервером как время выдачи + 24h. SHA-256 уместен для случайного высокоэнтропийного токена; он не заменяет затратное хеширование пароля.
- Для защищённого запроса общая функция аутентификации обработчика ищет хеш предъявленного bearer в БД, проверяет срок и получает пользователя. JSON-поля не задают субъект. Ошибка проверки или недоступная БД не дают доступ по умолчанию.
- Выход удаляет текущую серверную сессию; дальнейший запрос с этим токеном получает `401`. Истёкшая сессия не принимается независимо от момента её физического удаления.
- DTO профиля исключает хеши/пароль; обработчики и логи не выводят секреты. Исходный токен присутствует лишь в ответе на успешный вход.
- В одном процессе не более двух одновременных операций хеширования/проверки пароля. Избыток запросов входа/регистрации получает `503 authentication_busy`, чтобы память Argon2 не росла с каждым запросом. При чтении хеша из БД принимается только фиксированный поддерживаемый профиль, не произвольные затраты из повреждённой строки.

**Связанные угрозы:** [T-01](threat-model.md#t-01), [T-07](threat-model.md#t-07). **Требования:** [SR-01](requirements.md#sr-01), [SR-02](requirements.md#sr-02), [SR-08](requirements.md#sr-08).

**Обоснование и сравнение применимых вариантов:**

| Вариант | Выход и актуальность прав в TutorSpace | Цена и допущения |
| --- | --- | --- |
| Случайный токен + запись сессии в PostgreSQL | Удаление записи немедленно отзывает конкретную сессию. Сервер читает текущего пользователя и сможет читать текущую связь | Каждому защищённому запросу требуется БД; недоступность БД делает защищённый API недоступным |
| Подписанный JWT со сроком, субъектом и ролью | Сервис проверяет подпись без обращения к БД. Простое удаление токена у клиента не мешает предъявить его копию; прекращение связи/роли не отражается в уже выданных claims | Короткий TTL уменьшает окно, но не даёт немедленного выхода. Для него нужны denylist/версия сессии или проверка состояния, возвращающие серверное хранение; refresh добавляет протокол и обязанности |

Для небольшого одного сервера преимущество автономной проверки JWT не компенсирует механизм отзыва: предметные команды всё равно требуют БД. Серверные сессии выбраны ради простой наблюдаемой семантики logout и текущего состояния. Это сравнение не утверждает, что JWT сам по себе небезопасен; его применение уместно при иной границе доступности и явном протоколе отзыва. Если появятся автономные сервисы, которым нужен доступ при недоступной основной БД, выбор следует пересмотреть вместе с допустимым окном отзыва и способом распространения изменений прав.

**Будущая проверка:**

1. В тестовой БД создать A/B с одинаковыми паролями; проверить разные соли/хеши и отсутствие сырого пароля/токена ([SR-02](requirements.md#sr-02)). Значение `token_hash`, предъявленное как токен, даёт `401`.
2. Выполнить критерий [SR-01](requirements.md#sr-01): профиль A, поддельный токен, истёкший `expires_at`, logout/replay. Logout действует и при следующем запросе к другому процессу API с той же БД.
3. После получения токена остановить БД: защищённый запрос не возвращает профиль и даёт ошибку сервиса. После восстановления, если срок не истёк, действующий токен продолжает работать. Это проверяет выбранную цену доступности, а не только «правильный токен принимается».
4. Выполнить критерий [SR-08](requirements.md#sr-08) с маркерными секретами в ответах и штатных логах. Не использовать настоящие пароли.
5. В тестовом сценарии занять два слота вычисления пароля и отправить третий запрос: он получает `503 authentication_busy`, не запускает третье вычисление и не создаёт пользователя/сессию. Освобождение слота снова разрешает обработку. Проверить отклонение хеша с неподдерживаемыми параметрами без выделения памяти по этим параметрам.

**Ограничения и последствия:** bearer позволяет действие любому обладателю его копии до выхода/expiry. Запрос, уже прошедший аутентификацию одновременно с logout, может завершиться; гарантия отзыва относится к новым проверкам после успешного ответа logout. 24h — выбранный абсолютный срок учебного прототипа, без refresh и продления при обращении. Пароль длиной 12–128 байт сам по себе не гарантирует стойкость к угадыванию. Argon2 уменьшает скорость офлайн-перебора; лимит двух вычислений ограничивает память процесса, но не частоту попыток и не защищает от онлайн-перебора. Перед сетевым размещением нужна отдельная оценка нагрузки и ограничение попыток. HTTP через loopback не обеспечивает защиту в недоверенной сети. Доверенный DBA/владелец хоста может изменять записи; хеширование не защищает от такого администратора.

## D-02

**Согласованная связь и права на конкретный объект.**

**Контекст:** TutorSpace содержит пользователей одной роли с разными учениками и репетиторами. И роль, и наличие связи недостаточны без понимания, кто создал право и к какой именно работе оно относится. Прекращение занятий у репетитора не должно отдавать прошлые работы новому репетитору или лишать ученика результата проверки.

**Решение:**

- В слое предметных сервисов после аутентификации выполнять централизованные правила доступа: роль разрешает действие, идентификатор субъекта из сессии сопоставляется с участниками конкретного объекта. В SQL для списков и выбора объекта учитывать эту же область доступа; не сначала выдавать все записи и фильтровать на клиенте.
- Сервер назначает репетитора нового задания/интервала из сессии. Назначенного ученика проверяет по активной связи. Задание хранит неизменяемые `tutor_id` и `student_id`, занятие — исходных участников. ID из клиента лишь выбирает предполагаемый объект, не доказывает право на него.
- Создание приглашения доступно репетитору для выбранного ученика, но состояние сначала `pending`. Для пары `tutor_id`/`student_id` существует одна запись с уникальным ключом; повторное приглашение переводит прекращённую связь в `pending`, а не добавляет независимое основание доступа. Принять приглашение может только ученик, чей ID уже сохранён сервером; тогда состояние становится `active`. `tutor_id`/`student_id` принятого приглашения не меняются из тела запроса. Посторонний не принимает и не прекращает связь. Повторное приглашение не возвращает `active` без нового принятия учеником.
- Новые бронирования/задания требуют текущей `active` связи; её проверка выполняется в той же транзакции, что создание объекта. Все действия изменения состояния связи сериализуются с такими командами блокировкой той же записи. Если прекращение зафиксировалось первым, новая команда отклоняется; команда, закоммиченная до прекращения, остаётся старым объектом.
- Прекратить связь вправе любая сторона. Старые задания/решения/проверки остаются доступны только исходной паре; ученик сохраняет право отправки до проверки, прежний репетитор — проверки. Старое занятие видят и отменяют только его участники, независимо от текущей связи; новая связь с третьим лицом не передаёт историю.
- Недоступный объект возвращает `404` одинаково с несуществующим объектом; доступное роли действие для своего объекта выполняется. Недоступный тип действия по роли получает `403`. Отказы не меняют состояние и не раскрывают тело объекта.

**Обоснование:** роль ограничивает множество операций, согласие разрешает новую совместную работу, владение/участие ограничивает конкретную запись. Эти основания имеют разные жизненные циклы. Их явное разделение предотвращает «привилегию по ID» и случайную передачу истории. UUID вместо числового ID затруднил бы угадывание, но не заменил бы проверку известного ID; доверие клиентскому интерфейсу не подходит при curl/Postman.

**Связанные угрозы:** [T-02](threat-model.md#t-02), [T-03](threat-model.md#t-03), [T-05](threat-model.md#t-05), права отмены [T-04](threat-model.md#t-04). **Требования:** [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04), [SR-06](requirements.md#sr-06), [SR-05](requirements.md#sr-05).

### Контрпример к правдоподобной цепочке

Это разбор проектной гипотезы для проверки участниками, а не заявление о ранее выполненной ими работе или найденном дефекте в коде.

**Первоначальное правдоподобное предположение:** «проверять роль репетитора и наличие связи с учеником» выглядит достаточным для T-02 → SR-03 → D-02 → проверки доступа двух несвязанных пар.

**Конкретный контрпример:** посторонний C сам регистрируется как `tutor`, создаёт связь с учеником A, и сервер немедленно считает её действующей. C успешно проходит оба условия. Если запрос списка использует только «ученик входит в мои связи», C получает прошлые задания A, созданные репетитором B. Тест двух несвязанных пар это не обнаруживает: он не проверяет происхождение связи, и прежнее описание превращает недоверенное действие в право.

**Последствия и исправленная цепочка:** происхождение права выделено в [T-03](threat-model.md#t-03) и [SR-04](requirements.md#sr-04); D-02 требует `pending → active` с принятием только приглашённым учеником. Дополнительно [SR-03](requirements.md#sr-03) ограничивает старое задание исходным `tutor_id`, даже если ученик добровольно принял нового репетитора. Исправленная цепочка T-03 → SR-04/SR-03 → D-02 → проверка непринятого приглашения и непередаваемой истории покрывает оба условия, а не только наличие ссылки в таблице.

**Будущая проверка:**

1. Выполнить [SR-03](requirements.md#sr-03) на двух парах и чужих ID: GET, списки, изменение, отправка, проверка и отмена. Проверить состояние БД после отказов.
2. Создать приглашение C → A. До принятия C не создаёт задание, A не бронирует C. Посторонний ученик не принимает приглашение. После принятия A новые действия C/A разрешены; C всё ещё не видит старое задание B/A. Это проверяет уточнённую цепочку контрпримера.
3. Прекратить связь B/A: новое задание/бронирование B/A отклоняются, старые работа и результат видны B/A; C не видит их. Старое занятие отменяет только один из его участников.
4. Параллельно запустить прекращение связи и создание нового объекта. Если прекращение закоммичено первым — новый объект отсутствует; если создание первым — объект принадлежит исходным участникам и сохраняет доступ по правилу старых объектов.

**Ограничения и последствия:** активное согласие ученика не проверяет квалификацию репетитора, а добровольно принятая связь не означает доверие ко всем запросам этого репетитора. Сервис пока не предлагает передачу истории, модерацию, роли администратора или восстановление ошибочно прекращённой связи. Описанная политика сохранения доступа должна быть подтверждена участниками до реализации; при изменении смысла удаления/согласия SR-03/SR-04 и будущие проверки изменяются совместно.

## D-03

**Проверенная команда и атомарное изменение в PostgreSQL.**

**Контекст:** API превращает полностью управляемый клиентом JSON в сохранённые команды. Даже разрешённая команда может прийти дважды или конкурировать с другой. Нельзя полагаться только на предварительное чтение состояния или mutex одного процесса: данные переживают запрос и могут использоваться двумя экземплярами Go API.

**Решение:** для границы «ввод API → доверенное состояние PostgreSQL» использовать несколько обязательных, явно разных правил:

1. **Разбор и поля команды.** DTO содержит только разрешённые входные поля. `http.MaxBytesReader` ограничивает тело минимальной основы 4096 байт; JSON decoder отклоняет неизвестные поля и требует EOF после одного значения. Проверка типов/пределов происходит до записи. Логин ASCII `[a-z0-9_]{3,32}`, имя 1–80 Unicode-символов без управляющих после удаления крайних пробелов, пароль 12–128 байт UTF-8 без изменения пробелов. Для будущих текстовых команд нужны отдельные пределы, согласованные с размером задания/решения. Эти проверки не заменяют авторизацию.
2. **SQL как код сервера.** Структура запросов задаётся в коде, клиентские значения передаются через параметры `pgx` (`$1`, `$2`, ...). Динамические столбцы/операторы, если понадобятся, выбираются только из серверного списка. Не возвращать пользователю сырой SQL/ошибки подключения; внутренние сообщения не содержат значений пароля/токена/DSN.
3. **Инвариант занятия.** В будущем `bookings` хранит статус, а частичный уникальный индекс по `interval_id` для активного статуса допускает максимум одно активное занятие. Бронирование выполняется транзакцией: блокировать запись связи, проверить `active`, затем блокировать интервал `SELECT ... FOR UPDATE`, проверить свободное состояние и создать занятие. Статус доступности выводится из активного бронирования, отдельный независимый флаг «свободен» не хранится.
4. **Все пути отмены.** Транзакция находит интервал старого занятия, блокирует его, повторно читает занятие и проверяет исходных участников. Меняет только конкретное занятие `active → cancelled`; повтор для уже отменённой записи не влияет на новые записи. При отсутствии создания/удаления интервала это же блокирование синхронизирует конкурентные отмены и бронирования. Связь нужна для новых действий, но не для отмены старого занятия. Удаление/перенос интервала не добавляются без аналогичного правила.
5. **Пересечение разных интервалов.** Создание интервала блокирует строку его репетитора, проверяет `start < end` и отсутствие пересечения `[start, end)` с его существующими интервалами, затем записывает интервал в одной транзакции. Все создания проходят этот путь. Это исключает гонку двух параллельных «непересекающихся по предварительному чтению» вставок; соседние интервалы разрешены.
6. **Инвариант проверки.** Отправка и проверка блокируют одну строку задания/решения, повторно проверяют участников и состояние. Разрешены `issued → submitted`, замена текста в `submitted` и `submitted → reviewed`; `reviewed` окончателен. Каждая отправка увеличивает серверную целочисленную ревизию решения, возвращаемую вместе с текстом. Команда проверки обязательно предъявляет просмотренную репетитором ревизию; под блокировкой она сравнивается с текущей. Совпадение позволяет сохранить оценку/комментарий и проверенную ревизию в той же транзакции; несовпадение получает `409` без результата. Блокировка сама по себе не защищает от устаревшего текста, прочитанного в предыдущем GET. Поля авторства/статуса не копируются из JSON. При конфликте состояния операция также получает `409` без частичного изменения.

**Обоснование:** параметры отделяют данные от SQL-кода; ограниченный DTO предотвращает неожиданные поля; транзакция связывает актуальные проверки с записью; ограничения БД дают дополнительную защиту инвариантам, независимо от числа процессов. Это не один универсальный механизм: каждое правило закрывает свой переход на одной границе доверенного сохранения. Только проверка «интервал свободен» в Go проще, но имеет окно между чтением и записью; только уникальный индекс запретит дубль, но без транзакционной политики не определит корректную отмену и прекращение связи. Выбранное сочетание яснее для небольшого монолита с одной PostgreSQL.

**Связанные угрозы:** [T-04](threat-model.md#t-04), [T-05](threat-model.md#t-05), [T-06](threat-model.md#t-06), [T-08](threat-model.md#t-08), ошибки/диагностика [T-07](threat-model.md#t-07). **Требования:** [SR-05](requirements.md#sr-05), [SR-06](requirements.md#sr-06), [SR-07](requirements.md#sr-07), [SR-08](requirements.md#sr-08). Участники и согласие задаются [D-02](#d-02), субъект — [D-01](#d-01).

**Будущая проверка:**

1. Минимальная основа: выполнить границы размеров/полей [SR-07](requirements.md#sr-07), SQL-строки и ошибки [SR-08](requirements.md#sr-08). Сверить, что отклонённый ввод не создал запись. Для каждого нового SQL-запроса при расширении продукта проверить использование параметров; тест одного логина не доказывает безопасность всех будущих запросов.
2. После реализации расписания: выполнить [SR-05](requirements.md#sr-05) на двух процессах API с общей PostgreSQL. Запустить синхронные бронирования; ожидается один успех, один `409`, одна активная запись. Отменить X, забронировать Y, повторить отмену X: Y остаётся активным.
3. Одновременно создать два пересекающихся интервала одного репетитора: сохраняется один, второй получает `409`. Создать `[10:00, 11:00)` и `[11:00, 12:00)`: оба допустимы. Неверный диапазон получает 4xx без записи.
4. Вызвать ошибку записи внутри транзакции (например, конфликт уникального ограничения) в тестовой среде: нет частично созданного занятия/изменения статуса. Сверить инвариант запросом к БД.
5. После реализации домашних заданий: выполнить [SR-06](requirements.md#sr-06). Репетитор читает v1 и её ревизию, ученик заменяет текст на v2, затем репетитор проверяет ревизию v1: `409`, оценка не записана. После чтения v2 её проверка разрешена. Дополнительно одновременно отправить/проверить текст и зафиксировать порядок коммитов: либо проверка первой сохраняет точную ревизию и отправка отклонена, либо отправка первой делает предъявленную ревизию устаревшей и проверка отклонена. После `reviewed` повтор получает `409` и не меняет запись.
6. При прекращении связи одновременно с созданием применять план [D-02](#d-02): одни и те же блокируемые строки и порядок блокировок используются во всех путях. Повторить отказ для чужого ID и проверить неизменность строк.

**Ограничения и последствия:** блокировки увеличивают задержку при конкуренции; их порядок задаётся одинаково для команд, затрагивающих одинаковые объекты (связь перед интервалом; для работы — связь перед заданием, если она требуется). Транзакции должны быть короткими; HTTP-запрос и SQL ограничены context/timeout. Политика повторного запроса не даёт произвольное повторение с побочным эффектом: отмена относится к ID занятия. Фактическую схему индексов, блокировки и таймауты необходимо подтвердить при реализации; их описание здесь не является миграцией. Предельный размер тела одного запроса не защищает от частой нагрузки, а параметризация не заменяет проверку владения. Прямое изменение таблиц доверенным оператором способно обойти прикладные правила и находится вне модели.
