# Модель угроз TutorSpace

[Паспорт](../PROJECT.md) · [Требования](requirements.md) · [Решения](design-decisions.md) · [Проверки и вклад](../CONTRIBUTIONS.md) · [ИИ](../AI_USAGE.md)

Модель описывает текущую основу и будущие модули. Сценарии ниже — возможные угрозы, а не найденные ошибки работающего приложения.

## Модель продукта

```text
Недоверенный клиент: JSON, ID, bearer-токен
    │ TB-01: HTTP
    ▼
Go API — один процесс
    ├─ пользователи и сессии [работают]
    ├─ связи, расписание, задания [план]
    │ TB-02: параметры SQL и транзакции
    ▼
PostgreSQL
    ├─ users, sessions [работают]
    └─ предметные таблицы [план]
```

Текущие маршруты: `/healthz`, `/readyz`, `/api/register`, `/api/login`, `/api/me`, `/api/logout`. Потоки: пароль → проверка аккаунта; токен → проверка сессии; разрешённая команда → чтение/запись БД. Будущие предметные команды дополнительно проверяют участников объекта.

**Допущения:** клиент может знать чужой ID и отправлять любые, в том числе параллельные, запросы. Роль выбирается при регистрации и не подтверждает квалификацию. Новая связь требует согласия, история принадлежит исходным участникам. Хост, API и оператор БД доверенные; случайная утечка БД/логов рассматривается. Локально используются loopback HTTP и тестовые данные. Видеосвязь, платежи, файлы и frontend вне продукта; внешняя сеть потребует TLS и защиты от перебора/нагрузки.

## Границы доверия

| Граница | Данные и необходимая проверка |
| --- | --- |
| TB-01: клиент → API | Пароль, токен, ID, роль, текст. Проверять ввод, сессию и права; вход не делает все команды доверенными |
| TB-02: API → PostgreSQL | Параметры и изменения состояния. Использовать SQL-параметры, ограничения и транзакции |
| TB-03: секреты → ответы, логи, Git, копия БД | Не раскрывать учётные данные; хранить хеши вместо исходных секретов |

Модули одного процесса не образуют отдельную сетевую границу. Предметные действия всё равно требуют проверки прав.

## Значимые объекты и свойства

[Объекты продукта](../PROJECT.md#5-значимые-данные-и-другие-объекты): учётные данные, связи, занятия, задания, решения и оценки. Защищаются конфиденциальность секретов и работ, подлинность пользователя, согласие на связь, целостность расписания и соответствие оценки тексту, доступность API.

## Угрозы

### T-01

**Чужой субъект или отозванная сессия.** Клиент подставляет чужой ID/роль, поддельный токен либо повторяет токен после logout/истечения. Доверие этим данным раскрывает профиль и разрешает чужие действия.

**Граница:** TB-01. **Приоритет: высокий** — обычный запрос может нарушить доступ во всём продукте. [SR-01](requirements.md#sr-01).

### T-02

**Доступ по чужому ID (BOLA).** Авторизованный ученик читает работу другого или отменяет чужое занятие; репетитор читает чужие задания. Проверка только роли раскрывает данные и нарушает расписание.

**Граница:** TB-01, будущие объекты и списки. **Приоритет: высокий** — ID не секрет, атака повторяется обычным API-клиентом. [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04).

### T-03

**Самостоятельное получение права.** C выбирает роль репетитора и создаёт связь с A без принятия. Если связь сразу активна, C получает новые действия; если доступ определяется только нынешней связью, ещё и старые работы другого репетитора.

**Граница:** TB-01/TB-02, будущие связи. **Приоритет: высокий** — чужой пароль не нужен, созданное атакующим право проходит обычную проверку. [SR-04](requirements.md#sr-04), [SR-03](requirements.md#sr-03), [контрпример](design-decisions.md#контрпример-к-правдоподобной-цепочке).

### T-04

**Гонка бронирования и повтор отмены.** Два ученика одновременно занимают один интервал; повтор отмены X ошибочно освобождает уже созданное Y. Раздельное чтение и запись нарушают целостность расписания.

**Граница:** TB-01/TB-02, будущие бронирования. **Приоритет: высокий** — конкуренция и сетевые повторы возникают даже случайно; mutex одного процесса не защищает несколько API. [SR-05](requirements.md#sr-05), [SR-03](requirements.md#sr-03).

### T-05

**Оценка другого текста.** Репетитор читает v1, ученик сохраняет v2, затем приходит оценка v1. Только роль, владелец, статус и блокировка записи не связывают оценку с прочитанным текстом. Возможны также отправка после оценки и подмена серверных полей.

**Граница:** TB-01/TB-02, будущие задания. **Приоритет: высокий.** Первоначальная оценка «средний, достаточно запрета отправки после проверки» пересмотрена: контрпример возникает до оценки при законных действиях и нарушает главный результат сценария. [SR-06](requirements.md#sr-06), [SR-07](requirements.md#sr-07), [разбор D-03](design-decisions.md#контрпример-оценка-относится-к-другому-тексту).

### T-06

**SQL-инъекция.** Клиент вставляет SQL-фрагмент в поле. Склейка SQL со строкой запроса позволяет читать или менять посторонние записи от имени приложения.

**Граница:** TB-01 → TB-02, текущие и будущие запросы. **Приоритет: высокий** — доступное поле может затронуть данные многих пользователей. Параметризация текущего API — защита, а не повод исключить угрозу. [SR-07](requirements.md#sr-07).

### T-07

**Утечка секретов.** Пароль/токен попадает в профиль, лог или Git; копия БД содержит исходные секреты. Читатель получает доступ с правами владельца.

**Граница:** TB-03. **Приоритет: высокий** — токен обходит пароль, а диагностика и репозиторий имеют дополнительных читателей. Хеширование не защищает от прямого изменения БД доверенным администратором. [SR-02](requirements.md#sr-02), [SR-08](requirements.md#sr-08), [SR-01](requirements.md#sr-01).

### T-08

**Большой или неоднозначный JSON.** Неограниченный размер, лишние поля или несколько значений расходуют ресурсы и допускают неоднозначную команду.

**Граница:** TB-01. **Приоритет: средний, вне приоритетного набора** — контур локальный и массовая внешняя нагрузка не допускается. Ограничение тела необходимо, но не предотвращает частые запросы/DDoS. [SR-07](requirements.md#sr-07).
