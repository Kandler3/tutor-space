# Модель угроз TutorSpace

[Паспорт продукта](../PROJECT.md) · [Требования](requirements.md) · [Решения](design-decisions.md)

Статус: черновик EK1, подготовленный с помощью ИИ и ожидающий содержательной проверки участниками. Модель описывает минимальную техническую основу и будущий продукт отдельно; сценарий угрозы не является сообщением об обнаруженной уязвимости.

## Модель продукта

```text
Недоверенный пользователь
  │ curl / Postman: JSON, ID объектов, Authorization: Bearer ...
  │ TB-01
  ▼
Go API, net/http — один серверный процесс
  ├─ users: регистрация, вход, сессия, собственный профиль, выход
  ├─ relationships: приглашение → принятие → прекращение [план]
  ├─ schedule: интервалы, бронирование, отмена [план]
  └─ homework: задание, решение, проверка [план]
  │ параметризованные SQL, проверенные команды, транзакции
  │ TB-02
  ▼
PostgreSQL
  ├─ users, sessions — минимальная основа EK1
  └─ связи, интервалы, занятия, задания, решения, проверки [план]
```

**Минимальная основа EK1:** `GET /healthz`, `GET /readyz`, `POST /api/register`, `POST /api/login`, `GET /api/me`, `POST /api/logout`; PostgreSQL хранит пользователей и серверные сессии. Доступность и состояние этой основы подтверждаются исходниками и воспроизводимым запуском по инструкции из паспорта, а не перечислением функций в этой модели.

**Пока планируется:** роли в предметных действиях, подтверждаемые обеими сторонами связи, расписание, домашние задания и объектная авторизация этих модулей. Вход и собственный профиль не подтверждают корректность будущих проверок чужих ID.

**Существенные допущения:**

- Любой пользователь может сформировать произвольный HTTP-запрос, узнать или подобрать ID объекта и сделать параллельные запросы. Клиентский интерфейс не ограничивает нападающего.
- При регистрации роль выбирается из `tutor`/`student`; отдельной проверки квалификации репетитора нет. Именно поэтому роль не доказывает право на конкретного ученика.
- Связь даёт права на новые совместные действия только после принятия приглашения учеником. Права на старое задание/занятие задаются исходными участниками объекта, а не текущим репетитором ученика.
- API и PostgreSQL работают локально. HTTP допустим только для учебной демонстрации через loopback на доверенном хосте, с тестовыми данными. Внешнее размещение потребует пересмотра модели, TLS и защиты от автоматизированного перебора/нагрузки.
- ОС, контейнерный runtime, серверный процесс и оператор БД доверенные. Прямой доступ пользователя приложения к БД не предоставляется. Случайное раскрытие копии хранилища/логов рассматривается; злонамеренный DBA или полный захват хоста находятся за пределами обещаний приложения.
- Сторонняя видеосвязь, платежи, загрузка файлов и браузерный frontend отсутствуют; модель не добавляет их атаки к текущему продукту.

## Границы доверия

| Граница | Что пересекает | Почему требуется проверка |
| --- | --- | --- |
| TB-01: клиент → Go API | Пароль, bearer-токен, ID, роль, текст, команды изменения состояния | Пользователь контролирует запрос полностью; вход подтверждает субъекта, но не делает его команды или ссылки на объекты доверенными |
| TB-02: API → PostgreSQL | Параметры SQL, автор/владелец объекта, состояния, транзакции | Сервер должен преобразовать запрос в разрешённое изменение. SQL-параметры, ограничения и транзакции сохраняют инварианты даже при конкуренции процессов |
| TB-03: приватные учётные данные → ответы, логи, репозиторий, копия БД | Пароль/хеш, токен/хеш, строка подключения | Хранилища и каналы имеют разных читателей; технический доступ к диагностике не должен автоматически давать действующие сессии и пароли |

Между Go-модулями одного процесса нет отдельной сетевой границы доверия. Проверка роли/владения обязательна при каждом предметном действии, даже если запрос прошёл аутентификацию в модуле users.

## Значимые объекты и свойства

Полный предметный перечень находится в [разделе 5 паспорта](../PROJECT.md#5-значимые-данные-и-другие-объекты). Для модели критичны: конфиденциальность пароля, токена и работ ученика; корректность субъекта и связи; целостность состава участников/времени занятия; соответствие оценки действительно проверенному тексту; доступность API для обычного учебного запроса.

## Угрозы

### T-01

**Действие от чужого имени или после выхода.** Гость передаёт придуманный токен либо подставляет чужие `user_id`/`role`; бывший обладатель действующего токена повторяет его после logout/expiry. Если сервер доверяет предъявленному ID или не проверяет состояние сессии, он возвращает чужой профиль и разрешает действия от чужого имени.

**Нарушается:** подлинность субъекта; конфиденциальность и целостность объектов, доступных его аккаунту. **Граница:** TB-01, вход и все защищённые действия.

**Связанные требования:** [SR-01](requirements.md#sr-01). **Приоритет:** высокий, входит в приоритетный набор. Проверка требует обычного API-клиента; ошибка распространяется на оба основных сценария.

### T-02

**Обход владения через ID.** Ученик A со своей корректной сессией запрашивает решение ученика B по известному ID либо отменяет его занятие; репетитор A читает задания репетитора B. Если проверяется только роль, API раскрывает чужой текст/оценку или меняет чужое расписание.

**Нарушается:** конфиденциальность работ и целостность расписания. **Граница:** TB-01, объектные GET/команды и списки будущих модулей.

**Связанные требования:** [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04). **Приоритет:** высокий, входит в приоритетный набор. ID не является секретом; запрос легко повторить, а последствия касаются всех обычных пользователей.

### T-03

**Самостоятельное изготовление права через связь.** Посторонний зарегистрированный репетитор отправляет команду «связать меня с учеником A», или ученик B принимает чужое приглашение по его ID. Если само наличие строки связи считается достаточным без проверенного согласия, атакующий становится «своим» по формальной проверке и получает доступ к новым объектам ученика. Если новые отношения автоматически открывают историю ученика, атакующий увидит и работы прежнего репетитора.

**Нарушается:** согласие участников и границы доступа к их работе. **Граница:** TB-01/TB-02, создание/принятие связи и последующее использование её как основания прав.

**Связанные требования:** [SR-04](requirements.md#sr-04), [SR-03](requirements.md#sr-03). **Приоритет:** высокий, входит в приоритетный набор. Атакующему не нужен чужой пароль; роль репетитора выбирается им самим, а ошибочное право проходит обычные проверки связи. [Контрпример и уточнение](design-decisions.md#контрпример-к-правдоподобной-цепочке) раскрывают этот сценарий.

### T-04

**Гонка бронирования или повторная отмена.** Два ученика одновременно видят один свободный интервал и создают занятия; либо повторный запрос отмены старого занятия без привязки к текущей записи освобождает уже занятый другим учеником интервал. Чтение «свободен» и запись без атомарной проверки допускают две активные записи или ложную доступность.

**Нарушается:** целостность расписания; участники теряют надёжное время занятия. **Граница:** TB-01/TB-02, бронирование и все пути отмены будущего модуля расписания.

**Связанные требования:** [SR-05](requirements.md#sr-05), [SR-03](requirements.md#sr-03). **Приоритет:** высокий, входит в приоритетный набор. Параллельность возникает и случайно; повторный HTTP-запрос реалистичен при сетевом повторе, а серверный mutex одного процесса не защищает два экземпляра.

### T-05

**Подмена проверяемой работы.** Назначенный ученик повторно отправляет улучшенный текст после оценки или одновременно с проверкой; при свободном обновлении записи новый текст получает оценку, выставленную за старый. Даже без одновременных транзакций репетитор может прочитать v1, ученик отправить v2, а репетитор затем отправить оценку v1: проверка одного текущего статуса без ревизии ошибочно присвоит её v2. Подстановка `status`/оценки в тело также может обойти порядок проверки.

**Нарушается:** целостность решения и достоверность результата. **Граница:** TB-01/TB-02, отправка решения и проверка будущего модуля домашних заданий.

**Связанные требования:** [SR-06](requirements.md#sr-06), [SR-07](requirements.md#sr-07). **Приоритет:** средний, вне приоритетного набора. Последствия значимы, но ограничены собственной работой и требуют уже назначенного задания; чужие данные и расписание непосредственно не затрагиваются. Механизм всё равно предусмотрен в [D-03](design-decisions.md#d-03).

### T-06

**Текст запроса меняет смысл SQL.** Пользователь помещает SQL-фрагмент в логин, текст решения или идентификатор. Если будущий обработчик склеивает запрос со строкой клиента, приложение от имени своей DB-учётной записи может читать чужие задания или изменять записи вне проверенного объекта.

**Нарушается:** конфиденциальность и целостность данных нескольких пользователей. **Граница:** TB-01 → TB-02, построение SQL во всех модулях.

**Связанные требования:** [SR-07](requirements.md#sr-07). **Приоритет:** высокий, входит в приоритетный набор. Для эксплуатации достаточно поля API; последствия шире одной записи, поэтому будущие текстовые поля не оставлены вне модели. Параметризованные запросы минимальной основы — выбранная защита, не причина исключить риск при расширении кода.

### T-07

**Утечка учётных данных через диагностический канал или копию хранения.** Пароль/сырой bearer попадает в ответ профиля, лог запроса или публичный файл; другой читатель использует его для входа. При случайном чтении копии БД открытые пароли раскрывают доступ, а исходные токены позволяют вход без пароля.

**Нарушается:** конфиденциальность учётных данных и подлинность пользователя во всём приложении. **Граница:** TB-03, ответы, stdout/stderr, отслеживаемые файлы, строки `users`/`sessions`.

**Связанные требования:** [SR-02](requirements.md#sr-02), [SR-08](requirements.md#sr-08), [SR-01](requirements.md#sr-01). **Приоритет:** высокий, входит в приоритетный набор. Разглашение одного действующего токена обходит пароль и распространяется на все права владельца; публичный репозиторий и диагностика делают канал реалистичным. Это не модель злонамеренного DBA: хеширование не предотвращает прямое изменение таблиц доверенным администратором.

### T-08

**Чрезмерный или неоднозначный JSON.** Клиент отправляет многомегабайтное тело, неизвестные поля либо несколько JSON-значений; неограниченный/частичный разбор потребляет ресурсы или пропускает команды с неожиданными полями. Обычный учебный запрос не обслуживается либо сервер пишет частично понятные данные.

**Нарушается:** доступность API и целостность принятого ввода. **Граница:** TB-01, все принимающие JSON маршруты.

**Связанные требования:** [SR-07](requirements.md#sr-07). **Приоритет:** средний, вне приоритетного набора в локальном контуре на доверенном хосте. Внешняя массовая нагрузка сейчас не допускается; ограничение одного запроса всё равно необходимо. Перед сетевым размещением частоту запросов, длительность обработки и стоимость Argon2 следует оценить отдельно — предел тела не предотвращает DDoS.

## Приоритетный набор и трассировка

Выбраны **T-01, T-02, T-03, T-04, T-06, T-07**. Шесть угроз превышают примерный ориентир 3–5 в EK1, поскольку без искусственного объединения здесь отдельно видны вход, доступ к объектам, происхождение права, гонка расписания, SQL и разглашение секрета. Количество не является целью; последствия T-06/T-07 не занижены для попадания в ориентир. Все они покрыты тремя содержательными решениями:

| Угроза | Требуемое свойство | Решение и будущая проверка |
| --- | --- | --- |
| [T-01](#t-01) | [SR-01](requirements.md#sr-01) | [D-01](design-decisions.md#d-01): неверный/истёкший/отозванный токен и независимые аккаунты |
| [T-02](#t-02) | [SR-03](requirements.md#sr-03), [SR-04](requirements.md#sr-04) | [D-02](design-decisions.md#d-02): две пары, чужие ID, списки, смена связи |
| [T-03](#t-03) | [SR-04](requirements.md#sr-04), [SR-03](requirements.md#sr-03) | [D-02](design-decisions.md#d-02): приглашение без принятия, принятие посторонним, история прежнего репетитора |
| [T-04](#t-04) | [SR-05](requirements.md#sr-05), [SR-03](requirements.md#sr-03) | [D-03](design-decisions.md#d-03) и [D-02](design-decisions.md#d-02): конкурентные процессы и повторная отмена старой записи |
| [T-06](#t-06) | [SR-07](requirements.md#sr-07) | [D-03](design-decisions.md#d-03): SQL-фрагмент остаётся значением; другие строки не изменены |
| [T-07](#t-07) | [SR-02](requirements.md#sr-02), [SR-08](requirements.md#sr-08), [SR-01](requirements.md#sr-01) | [D-01](design-decisions.md#d-01) и [D-03](design-decisions.md#d-03): копия хранения, ответы и диагностика с тестовыми секретами |

T-05 и T-08 не исключены из работы: их критерии и механизмы описаны в SR-06/SR-07 и D-02/D-03. Будущие проверки следует выполнять на конкретной версии и только затем добавлять фактическое свидетельство.
